# Profile System Design

## Goal

Introduce **profiles** as a first-class concept in JSTorrent. A profile is a persistent identity that owns a set of torrents, download roots, and settings. Any frontend (Tauri desktop app, Chrome extension) can attach to a profile. This enables:

- Clean handoff between desktop app and extension (same profile, same state)
- Data isolation between Chrome profiles (separate profiles, separate state)
- Desktop app with profile picker (attach to any existing profile)
- Shared download roots when the user wants them

## Motivation

Today, the extension and desktop app each generate their own install ID independently:

- **Extension**: `getOrCreateTelemetryId()` in `extension/src/lib/telemetry-id.ts:7` generates a UUID, stores it in `chrome.storage.local` under key `telemetryId`
- **Tauri**: `get_or_create_install_id()` in `desktop/tauri-app/src-tauri/src/lib.rs:272` generates a UUID, stores it in `{app_data_dir}/install-id`

Both send their independent IDs to the native host during handshake (`installId` field). The host writes these into `rpc-info.json` profiles. This means:

1. The desktop app and extension always have different identities, even on the same machine
2. There's no way to share download roots or session state between them
3. The `rpc-info.json` profiles array stores per-profile data, but the SQLite KV store (`data.db`) is shared without any namespacing — session data collides

The profile system fixes this by making the host the owner of profile identity and routing all per-profile data through profile-scoped storage.

## Key Concepts

### Profile

A profile is:
- **ID**: UUID, generated by the host
- **Display name**: human-readable label (e.g., "Default", "Work", Chrome profile name)
- **Download roots**: list of `DownloadRoot` entries
- **Session data**: torrents, settings, stored in a profile-scoped SQLite database
- **Last used**: timestamp, for "most recent" heuristics

A profile is **not** tied to a specific frontend. Any frontend can create one or attach to an existing one.

### Frontend Modes

When a frontend connects, it operates in one of two modes:

- **Shared mode**: frontend attaches to an existing profile (or the host's default). The desktop app and extension see the same torrents, roots, settings. This is the clean handoff story.
- **Isolated mode**: frontend creates/uses its own profile. Each Chrome profile is a separate island.

The extension would have a setting to control this. The desktop app always picks from existing profiles (or creates one if none exist).

### Telemetry ID vs Profile ID

These are now fully separate concerns:

| | Telemetry ID | Profile ID |
|---|---|---|
| **Purpose** | Metrics, uninstall tracking | Session data, roots, identity |
| **Scope** | Per extension install | Per user profile |
| **Owner** | Extension (`chrome.storage.local`) | Host (`rpc-info.json`) |
| **Sent to host** | Never | In handshake |
| **Used by** | `registerDevice()`, `updateUninstallUrl()` | Session store, download roots, daemon pairing |

The extension's `telemetry-id.ts` continues to serve the metrics layer. It stops leaking into the host/daemon layer.

## Architecture

### Data Layout

```
~/.config/jstorrent-native/
  rpc-info.json              # Profile registry + current process info
  profiles/
    {profile-id-1}/
      data.db                # KV/session store for this profile
    {profile-id-2}/
      data.db
  data.db                    # Legacy (pre-profile) — migrates to first profile
```

### rpc-info.json (New Schema)

```json
{
  "version": 2,
  "default_profile": "uuid-of-default",
  "profiles": [
    {
      "id": "uuid-1",
      "display_name": "Default",
      "download_roots": [...],
      "created": 1707000000,
      "last_used": 1707500000
    },
    {
      "id": "uuid-2",
      "display_name": "Work",
      "download_roots": [...],
      "created": 1707100000,
      "last_used": 1707400000
    }
  ],
  "active": {
    "pid": 12345,
    "port": 7800,
    "token": "...",
    "launcher": "chrome",
    "profile_id": "uuid-1",
    "started": 1707500000
  }
}
```

Key changes from current schema:
- Profiles have an `id` field (the profile ID, replaces `install_id`)
- Process info (`pid`, `port`, `token`, `launcher`) moves to a single `active` block — only one frontend is active at a time (enforced by incumbent detection, see `docs/design/desktop-mutual-exclusion.md`)
- `default_profile` at top level for link handling and desktop app auto-attach
- `extension_id` and `browser` info move out of profiles (they're per-process, not per-profile)

### Handshake Protocol Changes

Currently, the handshake sends `installId` from the frontend to the host:

```json
{ "op": "handshake", "extensionId": "...", "installId": "..." }
```

New handshake adds profile negotiation. The frontend sends either a profile ID to attach to, or a request to create a new profile:

```json
{ "op": "handshake", "extensionId": "...", "profileId": "uuid-1" }
```

Or for first-time / new profile:

```json
{ "op": "handshake", "extensionId": "...", "profileId": null }
```

The host responds with `DaemonInfo` that now includes the resolved profile ID:

```json
{
  "type": "DaemonInfo",
  "payload": {
    "port": 7800,
    "token": "...",
    "version": "0.2.0",
    "roots": [...],
    "profileId": "uuid-1"
  }
}
```

The frontend stores the profile ID for future connections. Extension stores it in `chrome.storage.local`. Desktop app stores it in its own config.

### Desktop App Profile Selection

In Tauri's `host_handshake` command (`desktop/tauri-app/src-tauri/src/lib.rs:332`):

1. Instead of calling `get_or_create_install_id()`, query the host for available profiles
2. If one profile → auto-attach, send its ID in handshake
3. If multiple → show a profile picker dialog, remember choice
4. If none → send null, host creates a new profile

The `get_or_create_install_id()` function and the `install-id` file go away entirely.

### Extension Profile Selection

In `DaemonBridge.connectDesktop()` (`extension/src/lib/daemon-bridge.ts:636`):

- **Shared mode** (default): extension sends the profile ID it received from the host last time (stored in `chrome.storage.local`). If first connection and host has exactly one profile, auto-attaches. If host has zero profiles, host creates one.
- **Isolated mode**: extension always sends null (or a profile ID it "owns"), getting a dedicated profile.

The `getOrCreateTelemetryId()` call is removed from the handshake path. It remains only in `metrics.ts` and `sw.ts` for telemetry.

### KV Store Namespacing

The `KvStore` (`desktop/host/src/kv_store.rs:6`) currently opens a single `data.db`:

```rust
let db_path = config_dir.join("jstorrent-native").join("data.db");
```

With profiles, the host opens the profile-specific DB:

```rust
let db_path = config_dir
    .join("jstorrent-native")
    .join("profiles")
    .join(&profile_id)
    .join("data.db");
```

This is a one-line change in the path construction. The `KvStore` API is unchanged. Complete data isolation per profile with no schema changes.

### Session Store

The `HostChannelSessionStore` (`packages/client/src/host/host-channel-session-store.ts:28`) routes KV operations through the host channel. No changes needed — it's already indirected through the host, which will route to the correct profile-scoped DB.

## Link Handling

When a magnet link or .torrent file is opened externally, the host's RPC server receives it. With multiple profiles, the host must decide which profile to route to.

**Resolution cascade:**

1. **Active profile** — a frontend is currently connected using profile X → route to X
2. **Default profile** — `default_profile` is set in rpc-info.json → route to that
3. **Most recently used** — sort profiles by `last_used` descending → route to first
4. **Only one profile** — no ambiguity

The link is always routed immediately (no picker). If it lands in the wrong profile, the user fixes this by changing their default profile in settings.

**Relevant code:**
- Tauri deep link handler: `desktop/tauri-app/src-tauri/src/lib.rs:161` (`deep_link_event`)
- Host RPC magnet endpoint: `desktop/host/src/rpc.rs:97` (`add_magnet_handler`)

## Migration

### Existing Users (v1 → v2)

On first launch after upgrade:

1. Host reads `rpc-info.json` (version 1 format)
2. Creates a single profile from the existing data:
   - Profile ID = existing `install_id` (if present) or generate new UUID
   - Display name = "Default"
   - Download roots = existing roots from the profile entry
3. Moves `data.db` → `profiles/{profile-id}/data.db`
4. Writes new `rpc-info.json` (version 2 format)
5. Frontend receives the profile ID in handshake response, stores it

The extension's `chrome.storage.local['telemetryId']` continues to work for metrics. It just stops being sent to the host.

### ChromeOS / Android Companion

The ChromeOS path (`daemon-bridge.ts` HTTP flow and `chromeos-bootstrap.ts` WebSocket AUTH) currently sends `telemetryId` as the install ID:

- HTTP headers: `X-JST-InstallId` (`daemon-bridge.ts:374`) → rename to `X-JST-ProfileId`
- WebSocket AUTH frame: telemetryId bytes (`chromeos-bootstrap.ts:469`) → send profile ID instead
- Status check: `status.installId` comparisons (`daemon-bridge.ts:286,344,838`) → compare `profileId`

The Android companion daemon needs corresponding updates to recognize the profile ID.

## Settings UX

### Extension Settings

New setting in the extension preferences (would appear in `SettingsOverlay.tsx`):

- **Profile mode**: "Shared with desktop app" (default) / "Isolated"
  - Shared: uses the host's default profile → seamless handoff with desktop app
  - Isolated: uses a profile that belongs to this Chrome profile only

### Desktop App Settings

- **Active profile**: dropdown showing available profiles (hidden if only one)
- **Default profile for links**: which profile receives externally-opened torrents/magnets

### Preference: Preferred Frontend

A separate setting (also in `SettingsOverlay.tsx`) for the user to express which frontend they prefer:

- **Prefer desktop app**: when the desktop app launches, it takes over from the extension
- **Prefer extension**: when the extension connects, the desktop app yields (inverse of current behavior)

This interacts with the incumbent detection logic in `desktop/host/src/main.rs:71-107` and the TakeOver mechanism.

## Onboarding Flows & UX

### Binary Lifecycle Tiers

The Tauri binary has a progressive activation model. Users advance tiers by choice, never automatically.

1. **Invisible host** — .pkg installer registers native messaging manifest. Chrome launches the binary on demand via native messaging. No window, no tray, no dock icon. The user doesn't know it's running. This is the default state after install.

2. **Multi-profile aware** — A second Chrome profile installs the extension. It detects the existing native host and profile(s). The extension creates a new isolated profile by default and shows a notification: "JSTorrent created a new profile for this Chrome profile. To share torrents with your other profile, change this in Settings."

3. **Opened once** — User launches the .app from Applications (or clicks "Open desktop app" from extension settings). Sees the window with their existing torrents (attached to default profile). Closing the window exits the app.

4. **Activated desktop app** — User opts in to persistent desktop features: tray icon, start on login, background mode, external magnet link handling. This is a settings choice within the desktop app, not a default.

### macOS Packaging

The Tauri app ships as a **.pkg installer** (not DMG) on macOS. The .pkg:

- Contains the .app bundle (copied to `/Applications`)
- Runs a post-install script that writes the native messaging host manifest for Chrome
- Extension works immediately after install — no need to launch the app
- The .app in Applications retains Tauri's auto-updater for future updates
- The .pkg is just the delivery vehicle; after first install, the app updates itself

This avoids the DMG problem where the user must drag-to-Applications and then launch the app before the extension works. The .pkg handles registration silently.

On Windows (NSIS/WiX) and Linux (.deb), the installer already supports running setup steps during install, so no special handling needed.

### Extension-First Flow (Primary)

This is the most common onboarding path.

1. User installs extension from Chrome Web Store
2. Extension shows: "JSTorrent needs a companion app to connect to peers and save files to disk. [Install]"
3. User downloads and runs the .pkg installer
4. Extension is polling for native host availability (`chrome.runtime.connectNative()` on interval)
5. Native host appears — extension connects, receives profile ID
6. Extension shows success: "Connected. You're ready to go."
7. Soft pitch at this moment: "JSTorrent can also run as a standalone desktop app. [Open desktop app] / [Continue with extension]"
8. User's choice — either way, the extension is fully functional

**Detecting fresh install**: The extension sets `awaitingInstall: true` in `chrome.storage.local` while showing the install prompt. When the native host connects for the first time, the extension knows this is a fresh install transition (not a normal startup) and can show the appropriate success + discovery UX. This flag persists across extension restarts, so even if the user closes and reopens the browser mid-install, the transition is handled correctly.

The host can also write `"installed": <timestamp>` to `rpc-info.json` on first launch. The extension can read this and if it's within the last few minutes, treat it as a fresh install even without the local flag.

### Desktop-First Flow (Reverse)

User installs the desktop app first, uses it, later installs the extension.

1. User installs extension
2. Extension connects, detects native host with one existing profile
3. **Auto-attaches to the existing profile silently** — no prompt
4. User's torrents, settings, and download roots are immediately visible in the extension
5. No "create new or share?" question — the extension is the newcomer joining an established setup

This is the smoothest case. The user's mental model is "I added the extension as a convenience" and seeing their existing torrents confirms it's working.

### Second Chrome Profile Flow

User has JSTorrent working in their primary Chrome profile. They install the extension in a second Chrome profile (e.g., Work, NSFW).

1. Extension in second Chrome profile connects, detects existing profile(s)
2. **Creates a new isolated profile by default** — no prompt asking to share
3. Shows notification: "JSTorrent created a new profile for this Chrome profile. To share torrents with your other profile, change this in Settings."
4. User starts fresh in this profile — complete data isolation

**Rationale**: Users with multiple Chrome profiles generally expect separation. A user with an NSFW profile definitely doesn't want those torrents leaking into their main profile. Isolated-by-default is the safe choice.

### Profile Attachment Controls (Extension Settings)

The extension settings show the current profile attachment state with a toggle:

**When shared**: "Profile: Shared with desktop app [Use separate profile]"
- Switching to separate creates a new empty profile
- Warning: "Your current torrents and settings will stay with the shared profile. The extension will start fresh. [Continue / Cancel]"

**When isolated**: "Profile: Separate [Share with desktop app]"
- Switching to shared attaches to the default profile
- Warning: "Torrents in your current separate profile won't be merged. You may need to re-add them. [Continue / Cancel]"

### Desktop App First Launch (With Multiple Profiles)

When the desktop app is opened for the first time and multiple profiles exist:

- **Shows the default profile** — the first profile created, which is the "main" one
- No profile picker dialog on launch
- Profile switching available in settings (dropdown, only visible when multiple profiles exist)
- Desktop app remembers last-used profile for subsequent launches

### Profile Display Names

Chrome does not expose the Chrome profile name to extensions. Profiles are identified by:

- **Default name**: "Profile 1", "Profile 2", etc. (numbered by creation order)
- **Context metadata**: torrent count, last used timestamp — helps users identify which is which
- **User-renamable**: When a second profile is created, the notification includes a [Name it] option. Users can also rename in settings at any time.

## Open Questions

1. ~~**Profile display names**~~: **Resolved.** Chrome doesn't expose profile names. Default to "Profile 1", "Profile 2". Show metadata (torrent count, last used) for identification. Users can rename.

2. **Profile deletion**: If a user deletes a profile, what happens to active torrents? Do we need a confirmation flow? Do we delete the `profiles/{id}/data.db` file immediately?

3. **Profile merging**: Punt. Users re-add torrents in the target profile if they want to consolidate. Switching from isolated to shared doesn't merge — warning explains this.

4. **ChromeOS multi-profile**: On ChromeOS, Chrome profiles work differently (each is essentially a separate user). Does the profile system still make sense there, or is it always 1:1?

5. **Multiple simultaneous frontends**: Currently, incumbent detection enforces single-active-frontend. Probably not worth solving now.

6. ~~**Default profile auto-selection**~~: **Resolved.** Desktop app shows default profile on first launch, remembers last-used for subsequent launches. No picker on launch — switch in settings.

7. **Extension "owns" a profile**: When in isolated mode, should the profile store which extension ID created it? This would prevent the desktop app from accidentally attaching to an isolated profile. Or should all profiles be equal and the "isolation" is purely an extension-side setting?

8. **Auth token scope**: Currently each frontend connection gets its own auth token. With profiles, should the token be per-profile (so reconnecting to the same profile reuses the token) or remain per-connection? Per-connection is simpler and more secure.

9. **Extension standalone experience**: What does the extension do before the native binary is installed? Options: (a) parse/preview torrent metadata without downloading, (b) let users queue torrents and configure settings so everything is ready when the binary is installed, (c) just show the install prompt. Currently (c).

## Phases

1. **Host-owned profile ID**: Host generates profile ID, returns in handshake. Both frontends adopt it. `rpc-info.json` v2 schema. Migration of existing users. This is the foundational change.

2. **Per-profile SQLite**: Move `data.db` into `profiles/{id}/` directory. Host opens the correct DB based on active profile.

3. **Desktop profile picker**: Tauri queries available profiles, auto-selects or shows picker. Remembers last choice.

4. **Extension profile mode setting**: UI to choose shared vs isolated. New profiles created in isolated mode.

5. **Link handling cascade**: Route external magnets/torrents to the right profile.

6. **Preferred frontend setting**: User chooses whether desktop or extension takes priority in incumbent detection.
